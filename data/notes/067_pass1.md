Snowflake — research notes (Developer, Infra and Data platforms)

- Product: Snowflake is a cloud data platform for SQL analytics, data engineering, governance, and AI/ML workloads.
- Docs URL: https://docs.snowflake.com/en/developer-guide/snowflake-rest-api/reference

Auth model
- auth_methods: OAuth2; JWT/service account (key pair JWT); Bearer/PAT token; Workload identity federation
- primary_auth: OAuth2 (Snowflake OAuth “custom client” or External OAuth)
- How to get credentials: Create a Security Integration (OAuth) in the Snowflake account to register a client and obtain client_id/secret or configure key-pair OAuth; alternatively generate a PAT for a user.

Access and gating
- access: self_serve_trial (self-service 30‑day trial yields a full Snowflake account that can create Security Integrations and use APIs)
- production caveats: An ACCOUNTADMIN (or role with CREATE INTEGRATION) in each customer account must create/configure the OAuth security integration and allow your redirect URIs/scopes; no Snowflake marketplace/app review is required for custom OAuth clients.

API surface
- api_breadth: broad (GA REST APIs covering accounts, users/roles, warehouses, databases/schemas, tables/views, stages, tasks/streams, tags, alerts, security policies, functions/procedures, services/container resources, and more; plus the SQL API for statement execution)
- OpenAPI spec: Yes (official specs published in the snowflakedb/snowflake-rest-api-specs repo)
- Webhooks: Yes via Notification Integrations (first‑class support for outbound webhooks to Slack, Microsoft Teams, PagerDuty, Jira, ServiceNow; also cloud queues: SNS, Event Grid, Pub/Sub)
- Sandbox: Yes — self-service trial account

MCP
- mcp: official (Snowflake-managed MCP server and Snowflake-Labs OSS MCP servers exist)

Buildability for a Composio agent toolkit
- buildability: ready_with_caveats
- rationale: Public, well-documented REST APIs with OAuth2/PAT/JWT auth and OpenAPI specs; however, each customer must create/configure an OAuth Security Integration or provide a PAT/service user and base account URL. Network policies and role scoping are common enterprise prerequisites.
- blocker: other (customer-admin OAuth/PAT setup and per-account endpoints)

Additional implementation notes (for Composio)
- Base URL is per-account (e.g., https://<account>.snowflakecomputing.com); toolkit must capture account identifier/region and handle 202 async responses and paginated results via the Results API. ([docs.snowflake.com](https://docs.snowflake.com/en/developer-guide/snowflake-rest-api/getting-started?utm_source=openai))
- Preferred multi-tenant auth for end-user consent is Snowflake OAuth custom client (OAUTH_CLIENT=CUSTOM) with role-scoped scopes; service-account flows can use PAT or key‑pair JWT with strict role/network policy. ([docs.snowflake.com](https://docs.snowflake.com/en/user-guide/oauth-custom?gclsrc=3p.ds))
- OpenAPI specs can seed codegen and Postman collections; Snowflake publishes official spec repo. ([github.com](https://github.com/snowflakedb/snowflake-rest-api-specs))
- Webhooks are supported via Notification Integrations (Slack/Teams/PagerDuty/Jira/ServiceNow) and cloud queues; use SYSTEM$SEND_SNOWFLAKE_NOTIFICATION or product features (alerts, tasks) to emit. ([docs.snowflake.com](https://docs.snowflake.com/en/user-guide/notifications/webhook-notifications?utm_source=openai))

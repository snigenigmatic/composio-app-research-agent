Research notes:
- auth_methods: OAuth2; Bearer/PAT token (Personal Access Token). You’ll likely use OAuth for multi-user apps; PATs are long‑lived tokens for scripts and prototyping. ([developers.asana.com](https://developers.asana.com/docs/oauth?utm_source=openai))
- primary_auth: OAuth2 (Asana Connect/OAuth 2.0 for apps that act on behalf of many users). ([help.asana.com](https://help.asana.com/s/article/api?language=en_US&utm_source=openai))
- access: app_review — Devs can self‑serve create OAuth apps/PATs in the developer console, but submitting for review is required if you want to make the app available to users “in any Asana workspace, beyond your own organization” or list it publicly. ([developers.asana.com](https://developers.asana.com/docs/manage-and-share-your-app?utm_source=openai))
- api_breadth: broad — API covers many resources across the Work Graph (tasks, projects, portfolios, goals, custom fields, etc.). ([developers.asana.com](https://developers.asana.com/docs/object-hierarchy?utm_source=openai))
- mcp: official — Asana offers an official Model Context Protocol (MCP) server. ([developers.asana.com](https://developers.asana.com/docs/mcp-server?utm_source=openai))
- buildability: ready_with_caveats — The REST API is well‑documented with self‑serve creds, webhooks, and an OpenAPI spec; public multi‑tenant distribution will require Asana’s app review. ([developers.asana.com](https://developers.asana.com/docs/overview?utm_source=openai))
